    Set up QAEOps for a project

    This guide takes an existing software project from prerequisites to its first reviewed QAEOps requirements report. It follows the implemented QAEOps 0.1.0 release-candidate workflow.

    What you will learn

    • Which local tools QAEOps needs.
    • How to create a project-local .qai workspace safely.
    • How to connect QAEOps to LM Studio and verify readiness.
    • How to run and review the first project workflow.
    Human review is required. QAEOps produces advisory testing artifacts. A testing professional remains responsible for correctness, coverage, and project-specific decisions.

    Next: Confirm the prerequisites.

    Prerequisites

    What you will learn

    • Which tools are required for installation and AI-assisted workflows.
    • Which versions and local services QAEOps currently supports.
    RequirementPurposeVerify
    Python 3.12–3.14Runs the QAEOps CLIpython --version
    uvRecommended isolated installation and locked development environmentuv --version
    GitSource checkout and team version controlgit --version
    LM StudioLocal provider for AI-assisted commandsStart its local server, then use qae doctor
    Local chat modelAnalysis, generation, review, and chatqae models --type llm

    Docker is optional. It is needed only when the team chooses the container workflow.

    Install QAEOps

    What you will learn

    • How to install the current release candidate from a trusted local wheel.
    • How contributors can run the repository with locked dependencies.
    • How to verify the installed command.
    QAEOps 0.1.0 is not yet published to a public package index. Use a trusted local wheel or the source repository. Public uv tool install qaeops and pip install qaeops commands apply only after publication.

    Install a trusted local wheel

    uv tool install dist/qaeops-0.1.0-py3-none-any.whl
qae --version
qae --help

    Set up the source repository

    git clone https://github.com/CliffordVillanoy/qaeops.git
cd qaeops
uv sync --frozen --extra dev --python 3.12
uv run pytest
uv run qae --version

    An editable pip alternative for contributors is python -m pip install -e ".[dev]".

    Set up LM Studio

    What you will learn

    • How to prepare the implemented local model provider.
    • How to choose the endpoint and model identifier used by the project.
    1. Install LM Studio separately from an approved source.
    2. Download and load a chat model that fits the machine's RAM, VRAM, storage, and context limits.
    3. Start LM Studio's OpenAI-compatible local server.
    4. Keep the default endpoint http://localhost:1234/v1, or record the approved local endpoint.
    5. Use the exact model identifier reported by qae models --type llm.
    QAEOps does not install or launch LM Studio, download models, or enable telemetry. Model quality varies; validate a chosen model with representative project inputs.

    Initialize the project

    What you will learn

    • How to initialize QAEOps inside an existing project.
    • Which project-local files and directories are created.
    • How optional samples and provider checks behave.
    cd path/to/your-project
qae init

    The command creates .qai/config.yaml, .qai/config/, .qai/templates/, .qai/reports/, and .qai/workspace/. It adds only missing runtime entries to .gitignore. Re-running the command is idempotent and does not contact the network by default.

    Optional initialization checks

    qae init --sample
qae init --check-provider

    --sample creates example requirements, bug-report, and test-case files without replacing existing samples. --check-provider explicitly verifies the configured local provider. Use --force only for intentional recovery; it backs up the configuration and preserves reports and templates.

    Configure QAEOps

    What you will learn

    • How to set the local provider, project paths, and redaction default.
    • How to validate settings without placing secrets in YAML.
    provider:
  type: lmstudio
  base_url: http://localhost:1234/v1
  model: exact-model-id
  timeout_seconds: 30
workspace:
  reports: .qai/reports
  templates: .qai/templates
security:
  redact_by_default: true
    qae config path
qae config show
qae config validate
qae config set provider.timeout_seconds 30

    Supported environment overrides are QAI_PROVIDER_BASE_URL, QAI_PROVIDER_MODEL, and QAI_PROVIDER_TIMEOUT_SECONDS. If the local endpoint requires authentication, provide the token only through QAI_LMSTUDIO_API_TOKEN; do not store it in project YAML.

    Verify readiness

    What you will learn

    • How to check installation, workspace, configuration, and provider health.
    • How to confirm the exact local model identifier before a workflow runs.
    qae --version
qae config validate
qae doctor --verbose
qae models --type llm

    Resolve every required doctor failure before running an AI-assisted command. Help, version, initialization, configuration inspection, and local checks remain available when LM Studio is stopped; provider-backed workflows require a reachable server and loaded model.

    Run the first workflow

    What you will learn

    • How to prepare a real project requirements file.
    • How to run requirements analysis with the verified local model.
    • Where to find and how to review the result.

    Create a UTF-8 Markdown or text file inside the project, for example requirements.md, containing the actual feature requirements and acceptance criteria.

    qae analyze requirements.md --model "exact-model-id"

    QAEOps validates and redacts the input, calls only the configured local provider, validates the response, and writes a Markdown report under .qai/reports/ when the command's save workflow is selected.

    Review before use: Check assumptions, risks, ambiguities, suggested tests, missing coverage, and project terminology against the source requirements.

    An optional project conversation can be started with qae new --project . --title "Project QA planning".

    Team workspace practices

    What you will learn

    • Which QAEOps files are useful to share with a team.
    • How to keep generated artifacts and credentials controlled.
    • Review and version .qai/config.yaml when the settings are safe and portable for the team.
    • Version approved templates that define team conventions.
    • Keep generated reports, logs, caches, and local transcripts under the project's ignore policy unless the team deliberately reviews and publishes them.
    • Never store provider tokens or other secrets in configuration or source files.
    • Review generated artifacts before they enter tickets, test suites, or release evidence.

    Shell completion

    What you will learn

    • How to generate completion for a supported shell.
    • Why profile changes remain an explicit user action.
    qae completion powershell
qae completion bash
qae completion zsh
qae completion fish

    QAEOps prints completion locally and does not modify a shell profile automatically. Save or source the generated script according to the shell and your organization's profile policy.

    Offline preparation

    What you will learn

    • What must be downloaded before disconnecting.
    • Which operations stay local after preparation.
    • Install QAEOps and resolve all Python dependencies.
    • Install LM Studio and download a suitable model.
    • Keep project inputs, templates, and required package caches locally available.
    • Run qae doctor --verbose and a representative workflow before going offline.

    After preparation, model-assisted workflows require no internet and contact only the configured local endpoint. Installation, dependency resolution, LM Studio installation, and model download may require internet, a trusted cache, or an approved internal mirror.

    Docker option

    What you will learn

    • How to run the CLI in the repository's optional Compose service.
    • How the container reaches LM Studio on the host.
    docker compose build
docker compose run --rm qaeops --version
docker compose run --rm qaeops doctor /workspace

    The project is mounted at /workspace. The image does not embed project data, credentials, model files, or LM Studio. On Windows and macOS Docker Desktop, configure the provider endpoint as http://host.docker.internal:1234/v1. Linux environments may require a host-gateway mapping or explicit host IP.

    Troubleshooting

    What you will learn

    • How to diagnose the most common installation, workspace, and provider failures.
    • Which safe recovery command applies to each failure.

    Start with qae doctor --verbose.

    ProblemResolution
    qae not found after uv installationRun uv tool update-shell, restart the terminal, and inspect uv tool list.
    Unsupported PythonUse Python 3.12, 3.13, or 3.14 and recreate the environment.
    Workspace missingChange to the intended project and run qae init.
    Invalid configurationCorrect the YAML or intentionally recover with qae init --force.
    LM Studio unavailableOpen LM Studio, load a model, start the server, then retry doctor and models.
    No models listedDownload or load a suitable chat model and restart the local server.
    Request timeoutWait for model loading or increase provider.timeout_seconds.
    Docker cannot reach LM StudioUse host.docker.internal and configure a Linux host gateway when required.

    Provider failures use exit code 6 and sanitized remediation. QAEOps does not print tokens, authorization headers, endpoint credentials, raw response bodies, or raw transport exceptions.
