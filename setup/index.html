    Set up QAEOps for a project

    This guide takes an existing software project from project requirements to its first reviewed QAEOps requirements report. It follows the implemented QAEOps 0.1.0 release-candidate workflow.

    What you will learn

    • Which local tools QAEOps needs.
    • How to create a project-local .qai workspace safely.
    • How to connect QAEOps to LM Studio and verify readiness.
    • How to run and review the first project workflow.
    Human review is required. QAEOps produces advisory testing artifacts. A testing professional remains responsible for correctness, coverage, and project-specific decisions.

    How the setup fits together

    Install the CLIInitialize the projectConnect LM StudioVerify and run

    The CLI owns project setup, validation, guardrails, and report publication. LM Studio owns the local model and its OpenAI-compatible server. Your repository owns the source requirements and the project-local .qai workspace.

    What a complete setup looks like

    CLI ready

    qae --version and qae --help run from a fresh terminal.

    Workspace ready

    The project contains a valid .qai/config.yaml and its support directories.

    Provider ready

    qae doctor can reach LM Studio and qae models lists a chat model.

    Workflow proven

    A real requirement is analyzed and its report is reviewed by a testing professional.

    Next: Review the requirements.

    Requirements

    What you will learn

    • Which tools are required for installation and AI-assisted workflows.
    • Which versions and local services QAEOps currently supports.
    RequirementPurposeVerify
    Python 3.12–3.14Runs the QAEOps CLIpython --version
    uvRecommended isolated installation and locked development environmentuv --version
    GitSource checkout and team version controlgit --version
    LM StudioLocal provider for AI-assisted commandsStart its local server, then use qae doctor
    Local chat modelAnalysis, generation, review, and chatqae models --type llm

    Docker is optional. It is needed only when the team chooses the container workflow.

    Understand what is required

    Python runs the packaged CLI. uv is the recommended way to isolate the tool or reproduce the locked contributor environment, while pip remains supported inside a chosen environment. Git is required only for a source checkout and normal team version control.

    LM Studio and a loaded chat model are required only when a command needs model assistance. Local commands such as help, version, initialization, and configuration validation remain useful before the provider is ready.

    Project access

    Run QAEOps as the account that owns the project. That account needs read access to project inputs and write access to .qai/reports/. The workspace initializer rejects unsafe targets, including unsupported symlink paths, rather than writing outside the intended project.

    Preflight

    python --version
uv --version
git --version

    A supported Python version is mandatory. A missing uv installation is a non-fatal doctor warning when QAEOps was installed with pip.

    Install QAEOps

    What you will learn

    • How to install the current release candidate from a trusted local wheel.
    • How contributors can run the repository with locked dependencies.
    • How to verify the installed command.
    QAEOps 0.1.0 is not yet published to a public package index. Use a trusted local wheel or the source repository. Public uv tool install qaeops and pip install qaeops commands apply only after publication.

    Install a trusted local wheel

    uv tool install dist/qaeops-0.1.0-py3-none-any.whl
qae --version
qae --help

    Set up the source repository

    git clone https://github.com/CliffordVillanoy/qaeops.git
cd qaeops
uv sync --frozen --extra dev --python 3.12
uv run pytest
uv run qae --version

    An editable pip alternative for contributors is python -m pip install -e ".[dev]".

    Choose the installation that matches the job

    SituationUseWhy
    Release-candidate evaluationTrusted local wheelTests the built package in an isolated tool environment.
    QAEOps developmentLocked uv syncUses the repository lockfile and development dependencies.
    Editable contributor workflowpip install -e ".[dev]"Runs directly from src/qai while source files change.

    Why the verification commands matter

    qae --version proves that the expected executable is on the current PATH. qae --help proves that command discovery loads without requiring LM Studio. For a source checkout, uv run pytest verifies the checked-out development state before it is used as the setup source.

    Installing or upgrading the package must not modify an existing project workspace. Uninstalling QAEOps also leaves .qai, templates, and reports in place.

    Set up LM Studio

    What you will learn

    • How to prepare the implemented local model provider.
    • How to choose the endpoint and model identifier used by the project.
    1. Install LM Studio separately from an approved source.
    2. Download and load a chat model that fits the machine's RAM, VRAM, storage, and context limits.
    3. Start LM Studio's OpenAI-compatible local server.
    4. Keep the default endpoint http://localhost:1234/v1, or record the approved local endpoint.
    5. Use the exact model identifier reported by qae models --type llm.
    QAEOps does not install or launch LM Studio, download models, or enable telemetry. Model quality varies; validate a chosen model with representative project inputs.

    Know the provider boundary

    QAEOps validates

    It checks the request, testing domain, safety, redaction, and returned structure.

    LM Studio serves

    It hosts the downloaded model and exposes the configured local API endpoint.

    The model assists

    It produces structured content whose usefulness still depends on model capability.

    The engineer decides

    They review every finding and artifact before project use.

    Confirm model discovery

    qae doctor
qae models --type llm
qae models --json

    The model table can include its type, display name, quantization, context window, and whether LM Studio reports it as loaded or selected. Copy the exact chat-model ID for configuration or a command-level --model override.

    qae doctor proves bounded endpoint readiness; it does not prove that every project input fits the model context window or that the model will produce acceptable QA output.

    Initialize the project

    What you will learn

    • How to initialize QAEOps inside an existing project.
    • Which project-local files and directories are created.
    • How optional samples and provider checks behave.
    cd path/to/your-project
qae init

    The command creates .qai/config.yaml, .qai/config/, .qai/templates/, .qai/reports/, and .qai/workspace/. It adds only missing runtime entries to .gitignore. Re-running the command is idempotent and does not contact the network by default.

    Optional initialization checks

    qae init --sample
qae init --check-provider

    --sample creates example requirements, bug-report, and test-case files without replacing existing samples. --check-provider explicitly verifies the configured local provider. Use --force only for intentional recovery; it backs up the configuration and preserves reports and templates.

    Resulting workspace

    .qai/
├── config.yaml
├── config/
├── templates/
├── reports/
└── workspace/
    LocationRole
    config.yamlUser-facing provider, workspace, security, and UI settings.
    templates/Default and team-specific artifact formats.
    reports/Validated reports published by QAEOps workflows.
    workspace/Optional samples and project-local working material.

    Safe repeat behavior

    A normal repeat preserves a valid configuration and repairs compatible missing support directories. Initialization is non-interactive unless --interactive is supplied. It contacts LM Studio only when --check-provider is explicitly requested.

    The sample option creates sample-requirements.md, sample-bug-report.md, and sample-test-cases.md under .qai/workspace/ and preserves existing sample files.

    Configure QAEOps

    What you will learn

    • How to set the local provider, project paths, and redaction default.
    • How to validate settings without placing secrets in YAML.
    provider:
  type: lmstudio
  base_url: http://localhost:1234/v1
  model: exact-model-id
  timeout_seconds: 30
workspace:
  reports: .qai/reports
  templates: .qai/templates
security:
  redact_by_default: true
    qae config path
qae config show
qae config validate
qae config set provider.timeout_seconds 30

    Supported environment overrides are QAI_PROVIDER_BASE_URL, QAI_PROVIDER_MODEL, and QAI_PROVIDER_TIMEOUT_SECONDS. If the local endpoint requires authentication, provide the token only through QAI_LMSTUDIO_API_TOKEN; do not store it in project YAML.

    Use one project configuration

    .qai/config.yaml is the only user-facing configuration file. Fields can be omitted because QAEOps supplies safe local defaults. A model may remain unset until the engineer selects an exact ID from model discovery.

    What validation protects

    • YAML syntax, declared value types, and supported values.
    • A valid HTTP provider URL and bounded timeout.
    • Report and template paths that stay inside the project workspace.
    • Allowlisted configuration keys; unknown and secret-like keys are rejected.

    qae config show displays validated, non-secret effective settings. qae config set validates the new value, creates a backup, and atomically replaces only the configuration file. It preserves templates and reports.

    Configuration commands do not contact LM Studio. Run qae doctor --verbose after validation when you need to test provider readiness.

    Verify readiness

    What you will learn

    • How to check installation, workspace, configuration, and provider health.
    • How to confirm the exact local model identifier before a workflow runs.
    qae --version
qae config validate
qae doctor --verbose
qae models --type llm

    Resolve every required doctor failure before running an AI-assisted command. Help, version, initialization, configuration inspection, and local checks remain available when LM Studio is stopped; provider-backed workflows require a reachable server and loaded model.

    Read each check correctly

    CommandWhat success establishes
    qae --versionThe expected CLI executable is available.
    qae config validateThe nearest workspace configuration is structurally valid.
    qae doctor --verbosePython, installation, workspace, permissions, configuration, security, endpoint, and offline readiness checks have actionable status.
    qae models --type llmLM Studio is reachable and reports available chat models.

    Ready state

    The project is ready for model-assisted work when doctor has no required failure, the reports directory is writable, and the intended chat model is visible. A warning about optional tooling can be evaluated separately from a provider or workspace failure.

    Expected failures use specific exit codes: workspace and file failures use 3, configuration failures 4, safety rejections 5, and provider failures 6. This makes the same checks usable in local scripts and CI without parsing decorative terminal output.

    Run the first workflow

    What you will learn

    • How to prepare a real project requirements file.
    • How to run requirements analysis with the verified local model.
    • Where to find and how to review the result.

    Create a UTF-8 Markdown or text file inside the project, for example requirements.md, containing the actual feature requirements and acceptance criteria.

    qae analyze requirements.md --model "exact-model-id" --save

    QAEOps validates and redacts the input, calls only the configured local provider, validates the response, and writes a Markdown report under .qai/reports/ when the command's save workflow is selected.

    Review before use: Check assumptions, risks, ambiguities, suggested tests, missing coverage, and project terminology against the source requirements.

    An optional project conversation can be started with qae new --project . --title "Project QA planning".

    Prepare useful source material

    Use a readable UTF-8 .md or .txt file inside the nearest QAEOps workspace. Include the feature goal, relevant user roles, business rules, acceptance criteria, constraints, and known exclusions. Clear source material improves the review value without weakening QAEOps validation.

    What happens during analysis

    1. QAEOps validates the command, file type, size, and workspace containment.
    2. It checks request completeness, testing intent, supported domain, and safety.
    3. Detected sensitive values are redacted before the configured local provider is called.
    4. The structured response is validated and normalized.
    5. --save publishes a collision-resistant Markdown report under .qai/reports/.

    Read the report

    # Windows PowerShell
Get-ChildItem .\.qai\reports\requirement-analysis-*.md |
  Sort-Object LastWriteTime |
  Select-Object -Last 1

# macOS or Linux
ls -lt .qai/reports/

    The report can contain an executive summary, extracted requirements and rules, missing information, ambiguities, risks, stakeholder questions, and testing recommendations. Compare every item with the original source and the product context.

    Team workspace practices

    What you will learn

    • Which QAEOps files are useful to share with a team.
    • How to keep generated artifacts and credentials controlled.
    • Review and version .qai/config.yaml when the settings are safe and portable for the team.
    • Version approved templates that define team conventions.
    • Keep generated reports, logs, caches, and local transcripts under the project's ignore policy unless the team deliberately reviews and publishes them.
    • Never store provider tokens or other secrets in configuration or source files.
    • Review generated artifacts before they enter tickets, test suites, or release evidence.

    A practical repository policy

    ArtifactSuggested treatmentReason
    .qai/config.yamlReview, then version when portableKeeps non-secret project settings consistent.
    .qai/templates/Version approved team templatesMakes expected artifact structure inspectable.
    .qai/reports/Ignore by default; publish deliberatelyGenerated reports can contain project-derived material.
    Local chat transcripts, logs, and cachesKeep under the project ignore policyThey are runtime material rather than reviewed source.
    Provider tokenEnvironment variable onlyQAEOps rejects secrets in YAML.

    Review gate

    Before sharing an artifact, compare it with its source, remove unsupported assumptions, confirm terminology, and decide whether it belongs in version control, a ticket, or release evidence. Local storage alone does not make generated content approved project evidence.

    Shell completion

    What you will learn

    • How to generate completion for a supported shell.
    • Why profile changes remain an explicit user action.
    qae completion powershell
qae completion bash
qae completion zsh
qae completion fish

    QAEOps prints completion locally and does not modify a shell profile automatically. Save or source the generated script according to the shell and your organization's profile policy.

    Safe completion behavior

    The command writes deterministic completion script content to standard output. It does not show the QAEOps banner, use color or progress animation, make a network request, or edit a profile. This lets the engineer inspect the script before choosing how their shell loads it.

    Verify after installation

    Open a new shell after applying an approved profile change, type qae, and use the shell's completion key to confirm command discovery. If completion fails, the CLI remains fully usable through normal commands.

    Offline preparation

    What you will learn

    • What must be downloaded before disconnecting.
    • Which operations stay local after preparation.
    • Install QAEOps and resolve all Python dependencies.
    • Install LM Studio and download a suitable model.
    • Keep project inputs, templates, and required package caches locally available.
    • Run qae doctor --verbose and a representative workflow before going offline.

    After preparation, model-assisted workflows require no internet and contact only the configured local endpoint. Installation, dependency resolution, LM Studio installation, and model download may require internet, a trusted cache, or an approved internal mirror.

    Prove offline readiness

    1. Complete installation and dependency resolution while approved sources are available.
    2. Start LM Studio, load the intended downloaded model, and run qae doctor --verbose.
    3. Run one representative saved analysis using real-shaped, non-sensitive test input.
    4. Disconnect external network access while retaining loopback access to localhost:1234.
    5. Repeat the workflow and confirm that the report is still produced locally.

    What still works without LM Studio

    Help, version, workspace initialization, samples, configuration inspection and validation, and local checks remain available. Provider-backed analysis, generation, review, and project chat require the configured local server and a suitable loaded model.

    Hosted CI deliberately does not download models or start LM Studio. Live-model validation is a separate local release check.

    Docker option

    What you will learn

    • How to run the CLI in the repository's optional Compose service.
    • How the container reaches LM Studio on the host.
    docker compose build
docker compose run --rm qaeops --version
docker compose run --rm qaeops doctor /workspace

    The project is mounted at /workspace. The image does not embed project data, credentials, model files, or LM Studio. On Windows and macOS Docker Desktop, configure the provider endpoint as http://host.docker.internal:1234/v1. Linux environments may require a host-gateway mapping or explicit host IP.

    Understand the container boundary

    ComponentRuns or lives
    QAEOps CLIInside the container
    Project filesMounted from the host at /workspace
    LM Studio and modelsOn the host
    Reports and workspace stateWritten back to the mounted project

    The same workspace containment and publication rules apply in the container. Use Docker when isolation or reproducible CLI packaging helps the project; it is not required for a normal local installation.

    Verify the bridge

    First prove the container can run --version. Then run doctor against /workspace. A provider failure at that point usually means the host endpoint or Linux host-gateway mapping needs correction, not that the project files are missing.

    Troubleshooting

    What you will learn

    • How to diagnose the most common installation, workspace, and provider failures.
    • Which safe recovery command applies to each failure.

    Start with qae doctor --verbose.

    ProblemResolution
    qae not found after uv installationRun uv tool update-shell, restart the terminal, and inspect uv tool list.
    Unsupported PythonUse Python 3.12, 3.13, or 3.14 and recreate the environment.
    Workspace missingChange to the intended project and run qae init.
    Invalid configurationCorrect the YAML or intentionally recover with qae init --force.
    LM Studio unavailableOpen LM Studio, load a model, start the server, then retry doctor and models.
    No models listedDownload or load a suitable chat model and restart the local server.
    Request timeoutWait for model loading or increase provider.timeout_seconds.
    Docker cannot reach LM StudioUse host.docker.internal and configure a Linux host gateway when required.

    Provider failures use exit code 6 and sanitized remediation. QAEOps does not print tokens, authorization headers, endpoint credentials, raw response bodies, or raw transport exceptions.

    Use the failure category

    Exit codeCategoryFirst place to look
    2Arguments or unsupported requestCommand help and supplied options
    3Workspace or fileProject directory, containment, and permissions
    4Configuration.qai/config.yaml and qae config validate
    5Security or safetyRejected input, path, or unsafe operation
    6ProviderLM Studio server, loaded model, endpoint, and timeout
    7Unexpected internal failureSanitized error details and reproducible command

    Recover without losing work

    Re-run qae init to recreate compatible missing support directories. Use qae init --force only when intentionally repairing configuration; it creates a backup and preserves reports and templates. Do not force-initialize an original workspace merely to make it compatible with an older QAEOps version.

    If provider output is invalid JSON, use a model that reliably follows structured instructions. The documented MVP qualification model is qwen/qwen3-4b-2507; smaller models may not satisfy every response schema.
