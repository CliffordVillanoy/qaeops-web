Why we built QAEOps

We believe testing judgment shouldn't be outsourced to a black box. QAEOps runs locally, structures the repetitive parts of QA work like analysis, test cases, and synthetic data, and leaves interpretation, execution, and final sign-off exactly where they belong: with the testing professional.

Frequently asked questions

Answers reflect the documented QAEOps 0.1.0 release-candidate functionality.

What is QAEOps?

QAEOps is a local-first command-line assistant focused on software Quality Engineering. Its implemented workflows cover requirements analysis, test-case drafting, synthetic test data, bug-report review, Playwright preparation and review, diagnostics, configuration, model discovery, and local project chat.

Who is QAEOps designed for?

It is designed for Software QA Engineers, Test Automation Engineers, SDETs, QA Leads, and software teams involved in test preparation and review. The interface assumes that a testing professional evaluates the generated results.

Does QAEOps replace a testing professional?

No. It prepares reviewable findings and artifacts. A professional still interprets requirements, selects coverage, verifies expected behavior, executes testing, evaluates evidence, and decides whether an output is suitable.

Which workflows use a local model?

Requirements analysis, test-case drafting, schema inference for synthetic data, bug review, Playwright assistance, and project chat use the configured LM Studio endpoint. Local validation runs before provider-facing work, and returned structures are checked before display or publication.

What is required to run AI-assisted commands?

Install the QAEOps CLI from a trusted local wheel or source checkout, install LM Studio, download and load a suitable chat model, and start its local server. Python 3.12–3.14 is supported by the documented release candidate.

What does local-first mean here?

The supported AI workflow connects to the configured LM Studio endpoint and uses a model available on the user’s machine. Some setup steps, including dependency installation, LM Studio installation, and model download, may still require internet access or an approved internal source.

How does QAEOps handle sensitive input?

Provider-facing commands apply request validation, supported-domain checks, safety controls, and sensitive-value redaction before contacting LM Studio. Errors avoid displaying credentials and raw transport details. Local-first operation is an architecture choice, not a security certification.

How is synthetic test data created?

The local model infers only a constrained field schema. Faker generates the records locally from an isolated seed. The implemented exporters support CSV, JSON, and SQL with format-specific validation and explicit overwrite behavior.

Does Playwright assistance create finished tests?

No. Generation produces deterministic starter files or an advisory report. Generated tests remain skipped with TODO markers until an engineer verifies application behavior, routes, locators, assertions, isolation, credentials, and cleanup.

Does QAEOps modify existing Playwright source during review?

No. Static review accepts a contained TypeScript file or directory, reports findings about locators, assertions, waits, page-object boundaries, secrets, and unsafe patterns, and leaves the source unchanged.

Are reports saved automatically?

Most generated results display first and are saved when the user selects the documented save or output behavior. Publications use contained destinations, collision checks, and atomic writes. Existing files require the applicable explicit replacement option.

Can the website run QAEOps workflows?

No. The implemented product interface is the qae command-line application. This website presents product information, current development status, and CLI documentation.

Is QAEOps available from a public package index?

No. Version 0.1.0 is documented as a release candidate. The current installation paths use a trusted locally built wheel or a source checkout.
