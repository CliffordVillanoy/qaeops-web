    Introduction

    QAEOps is a local-first command-line Quality Engineering Assistant for Software QA Engineers, Test Automation Engineers, SDETs, and QA Leads. It supports requirements analysis, test-case design, synthetic data, bug-report review, Playwright scaffolding and review, diagnostics, and local project chat.

    Human review is required. Generated findings, cases, data, severity suggestions, and automation are starting points. The testing professional decides what is correct and suitable.

    Current interface

    QAEOps is implemented as the qae command-line application. It supports both one-shot commands, such as qae doctor and qae analyze, and a persistent terminal session opened with qae. The installed command tree covers workspace setup, diagnostics, model discovery, configuration, requirements analysis, test-case generation, synthetic test data, bug review, Playwright generation and review, and project chat.

    Current provider

    LM Studio is the implemented model provider for version 0.1.0. QAEOps connects to its OpenAI-compatible local server, using http://localhost:1234/v1 by default, and works with a chat model loaded there. QAEOps validates and redacts provider-facing input, validates returned structures, and reports sanitized errors. It does not install LM Studio, download models, or start the server.

    Local artifacts

    qae init creates a project-local .qai workspace containing configuration, templates, reports, and workflow state. Generated reports are written within the configured project directories, and saved project-chat transcripts are stored under .qai/workspace/chats/. Workspace paths are checked for containment, and supported writes use preservation and atomic-publication rules.

    Project status

    QAEOps 0.1.0 is a release candidate with the documented CLI workflows implemented in the repository. The package is not yet published to a public package index, so current evaluation uses a trusted locally built wheel or source checkout. A browser product interface, cloud-model support, and universal HTML, PDF, and DOCX report exports remain planned rather than available features.

    Command name

    QAEOps installs the qae command. Use it at the start of every workflow you run from your operating-system terminal; the word that follows selects the task.

    qae doctor
qae analyze requirements.md
qae testcase requirements.md
qae playwright review tests/

    For example, qae doctor checks whether the local environment is ready, while qae analyze starts the requirements-analysis workflow. qaeops is the package name used for installation and is not the command you enter to run QAEOps.

    Architecture and data flow

    Testing professionalQAEOps CLIValidation and guardrailsLM Studio local model

    Provider-facing input passes deterministic validation, domain enforcement, safety checks, and redaction. The returned structure is validated before QAEOps renders or writes an artifact.

    1. The testing professional starts a workflow. They provide a supported QA command, project input, and any explicit output options through the qae CLI.
    2. The CLI validates local inputs. QAEOps checks command arguments, workspace paths, supported file types, UTF-8 content, request completeness, and applicable configuration before provider work begins.
    3. Guardrails run before LM Studio. QAEOps enforces software-testing intent and domain boundaries, rejects unsafe requests locally, and redacts detected sensitive values from provider-facing content.
    4. LM Studio processes the bounded request. The configured local chat model returns the structured content required by the selected workflow. QAEOps contacts only the configured LM Studio endpoint.
    5. QAEOps validates the response. Returned data is parsed, normalized, and checked against the workflow contract before it is displayed or published to a workspace-contained destination.
    6. The testing professional reviews the result. Findings, test cases, synthetic schemas, bug recommendations, and automation guidance remain advisory until a professional confirms them for the project.

    Core principles

    • 01
      Human first

      Output remains reviewable and modifiable.

    • 02
      Local first

      The supported model workflow runs through the local provider.

    • 03
      Deterministic guardrails

      Inputs, outputs, paths, and publications follow explicit validation rules.

    • 04
      Quality-engineering focus

      Supported requests must remain within software testing and QA.

    Choosing a model

    Select a chat model whose published RAM, VRAM, storage, architecture, and context requirements fit the device. A model appearing in LM Studio does not prove that it will follow every structured QAEOps response schema; validate it with representative project inputs.

    Install LM Studio and download a model before going offline. QAEOps does not install LM Studio, download models, enable telemetry, or start the local server.

    Quick start

    This flow initializes synthetic samples, verifies the local provider, and produces the first requirements report.

    1. Open an existing project

      cd "C:\My QA Project"

    2. Initialize samples

      qae init --sample

      Existing sample files are preserved.

    3. Start LM Studio

      Load a chat model and start the local server at http://localhost:1234/v1.

    4. Verify readiness

      qae doctor --verbose
qae models

      Copy the exact ID of a loaded chat model.

    5. Analyze the sample

      qae analyze path/to/sample-requirements.md \
  --model "your-local-model-name"

    6. Review the report

      Review the report path shown by QAEOps.

    • sample-requirements.md
    • sample-bug-report.md
    • sample-test-cases.md

    The first setup commands are safe to repeat. Analysis requires the input file and a running local provider. Review all findings before applying them.

    Open QAEOps

    Start the installed QAEOps terminal experience, check local-provider readiness, or inspect version information without beginning a testing workflow.

    Command

    qae
qae --run
qae --plain
qae --version
qae -v
qae --exit

    Bare qae shows the product identity and performs a short readiness check against the configured local LM Studio endpoint. In a terminal it continues to a persistent > command prompt. Enter new, doctor, or another supported command with or without the qae prefix.

    Startup outcomes

    StateBehavior
    Provider readyShows the prompt and accepts a supported command.
    Server unavailableShows installation and server-start guidance without exposing transport details.
    No model loadedShows distinct model download and load guidance.
    Redirected inputDoes not wait for an interactive session.

    Persistent command session

    • The prompt uses a minimal > marker and does not display a task menu before the user expresses intent.
    • Commands may omit the executable prefix, such as doctor, or include it, such as qae doctor.
    • Completing a command returns to the prompt without repeating the banner.
    • Startup readiness checks use the configured local endpoint and do not access the public internet or emit telemetry.

    One-shot options

    --plain removes ANSI decoration. --version reports QAEOps, build, Python, and configured provider versions without a provider request. --exit exits successfully when no session is active. Ctrl+C, /exit, exit, and quit end an active terminal session safely.

    Set up a workspace

    Create the local configuration, templates, reports, and workspace directories that QAEOps commands use within an existing project.

    Command

    qae init [PATH]
qae init --sample
qae init --type requirement
qae init --type complete
qae init --model MODEL
qae init --provider-url http://localhost:1234/v1
qae init --no-gitignore
qae init --check-provider
qae init --force

    Initializes an existing real directory and creates safe workspace resources. Traversal, file targets, symbolic-link targets, and symbolic-link workspace resources are rejected.

    Option behavior

    OptionBehavior
    --sampleAdds three synthetic inputs and preserves existing sample files.
    --typeSelects the requested workspace/sample setup type.
    --modelWrites the chosen local model to initial configuration.
    --provider-urlUses a different valid local OpenAI-compatible endpoint.
    --no-gitignoreLeaves the project’s .gitignore unchanged.
    --check-providerRuns a bounded provider check after local initialization.
    --forceBacks up and replaces only the workspace configuration file.

    The default run makes no network call. Repeated initialization is a successful no-op for compatible workspaces. Missing support directories are repaired, while reports, templates, extensions, and workspace state are preserved. Newly created resources are rolled back if initialization fails.

    Next: Run qae doctor.

    Check system health

    Inspect the installation, workspace, configuration, permissions, security checks, and local-provider readiness in one diagnostic run.

    Command

    qae doctor
qae doctor /path/to/workspace
qae doctor --verbose
qae doctor --json

    Runs environment, installed-version, workspace, directory, configuration, template, report, permission, provider, security, LM Studio connectivity, and offline-readiness checks. It reports all checks rather than stopping at the first failure.

    Reading the result

    • A passed check confirms the tested condition at that moment.
    • A warning is non-fatal and exits successfully.
    • A failed workspace, configuration, security, or provider check uses its corresponding exit code.
    • --verbose adds sanitized paths, endpoint, timeout, permissions, version source, and readiness details.
    • --json emits one machine-readable diagnostic document.

    Checks performed

    AreaWhat QAEOps verifies
    RuntimePython and installed QAEOps versions, plus optional uv availability.
    WorkspaceThe project workspace, required workspace directories, templates, reports, and permissions.
    ConfigurationReadable YAML, supported values, contained paths, and a sanitized provider endpoint.
    Local providerLM Studio connectivity, registered models, and current workflow readiness.
    SafeguardsSecurity self-checks and offline availability for commands that do not need a model.

    URL credentials, query strings, tokens, and raw provider transport details are not displayed. If LM Studio is unavailable, help, version, initialization, and local configuration validation remain usable.

    New-Item -ItemType Directory -Force (Split-Path $PROFILE) | Out-Null

    Create synthetic test data

    Infer a constrained field schema with the local model, then generate deterministic synthetic records locally with Faker.

    Command

    qae testdata
qae testdata "customers with unique email" \
  --format json --output reports/customers.json \
  --count 100 --seed 42 --locale en_US
qae testdata "orders with totals" \
  --format sql --output orders.sql --table orders
    OptionPurpose
    --formatSelect CSV, JSON, or SQL.
    --outputSelect a workspace-contained destination.
    --countGenerate 1–10,000 records; default 10.
    --seedSet the deterministic Faker seed; default 42.
    --localeSelect a Faker locale; default en_US.
    --modelOverride the local model used only for schema inference.
    --tableSet a validated SQL table name.
    --overwriteAtomically replace the selected existing file.

    How generation works

    1. QAEOps collects or validates the dataset requirement and format.
    2. The local model receives sanitized input and returns only a strict field schema.
    3. Faker creates all records locally from an isolated seeded instance.
    4. The selected exporter validates identifiers, values, size, and destination before atomic publication.

    Format safeguards

    CSV neutralizes spreadsheet formulas. JSON is stable strict UTF-8. SQL validates identifiers and escapes typed values. Validated records are immutable, destinations remain inside the workspace, and existing files require explicit overwrite behavior.

    Review: Confirm schema, locale, boundary cases, uniqueness assumptions, and that every record is synthetic.

    Generation behavior

    QAEOps accepts contained UTF-8 requirement files, sanitizes input, validates structured model output, and produces deterministic scaffolding and recommendations. Generated tests remain skipped with TODO markers until an engineer verifies application behavior, locators, and assertions.

    Review behavior

    Review accepts a contained TypeScript file or directory. Local static checks cover locator quality, assertions, waits, page-object boundaries, secrets, and unsafe patterns. Review writes a sanitized advisory report and never modifies source files.

    Review: Run generated code only after checking routes, selectors, test isolation, credentials, data cleanup, and expected behavior.

    Output and exit codes

    QAEOps separates terminal presentation from saved artifacts. Generation results display by default and are persisted only when the user requests it, except when a command’s explicit output workflow requires a destination.

    Presentation modes

    qae --plain doctor
qae --no-color doctor --verbose
qae --quiet models
qae --theme high_contrast doctor
    ModeContract
    RichDefault human-facing panels, tables, labels, and restrained color.
    --plainStable ASCII-oriented text without ANSI sequences.
    --no-colorPreserves semantic words and layout while removing color.
    --quietSuppresses routine success and guidance output.
    --jsonOne stable JSON document with no banner, progress, ANSI, or explanatory prefix.
    --stdoutRaw artifact content without presentation decoration.

    Global options appear before the command. QAEOps honors NO_COLOR; ASCII-compatible output is available when optional Unicode symbols must be avoided. CI, redirected, JSON, and stdout modes suppress progress animation.

    Saving artifacts

    --save creates a collision-resistant file. --save --force targets only the command’s canonical report and never performs broad directory replacement. Interactive replacement asks for confirmation. Test-data --format selects CSV, JSON, or SQL; report commands currently support Markdown.

    Exit codes

    CodeMeaning
    0Success
    1Invalid command
    2Invalid arguments, unsupported feature, domain rejection, or clarification required
    3Workspace or file error
    4Configuration error
    5Security or safety rejection
    6Local provider error
    7Unexpected internal failure

    Failures use structured fields: title, reason, details, remediation, optional next command, and exit code.

    Validation and security

    Before provider-facing commands run, QAEOps validates command shape, arguments, workspace files, request completeness, intent, testing domain, and safety. This applies to analysis, test cases, test data, bug review, Playwright generation/review, and project chat.

    Decision flow

    1. Validate command arguments and required files.
    2. Confirm that the request is complete enough to execute.
    3. Classify intent and enforce the supported QA/testing domain.
    4. Reject unsafe requests locally.
    5. Redact detected sensitive values.
    6. Contact only the configured LM Studio endpoint.
    7. Validate and normalize provider output before rendering or writing.

    Ambiguous requests receive one focused clarification question and closed options only when useful. Rejected and ambiguous requests do not reach LM Studio.

    Storage and output safeguards

    • Workspace input and output paths are contained.
    • Writes use atomic publication and explicit replacement rules.
    • Configuration commands reject unknown and secret-like keys.
    • Raw transport exceptions, tokens, headers, endpoint credentials, and unsafe input are not reflected in errors.
    • Saved chat transcripts contain sanitized content.
    Local-first describes the supported model workflow. Review the operating system, LM Studio configuration, extensions, mounted storage, and connected tools against organizational data-handling requirements. It is not a security certification.

    Docker and offline use

    Build and run

    docker compose build
docker compose run --rm qaeops --version
docker compose run --rm qaeops doctor /workspace

    Project files are mounted at /workspace. The image does not embed project data, credentials, or model files. LM Studio runs on the host and is not included in the Compose stack.

    Reach the host provider

    Windows and macOS Docker Desktop use http://host.docker.internal:1234/v1. Current Linux Compose setups can map this name to the host gateway; older environments may require an explicit host IP through the provider URL configuration.

    Prepare for offline work

    • Install QAEOps and all Python dependencies.
    • Install LM Studio separately.
    • Download at least one suitable model.
    • Keep required project inputs available locally.

    Container boundaries

    ComponentLocation
    QAEOps CLIRuns inside the container.
    Project filesMounted from the host at /workspace.
    LM Studio and modelsRemain on the host and are reached through the configured local endpoint.
    Reports and workspace stateWritten to the mounted project with the same containment rules as a local run.

    Available without the provider

    Help, version, initialization, configuration inspection and validation, and local checks remain available while LM Studio is stopped. qae doctor and qae models provide safe remediation when provider readiness is missing.

    After preparation, model-assisted workflows require no internet. Installation, dependency resolution, LM Studio installation, and model download may require internet, a trusted cache, or an approved internal mirror.

    Troubleshooting

    Start with:

    qae doctor --verbose
    ProblemResolution
    qae is not found after uv installationRun uv tool update-shell, restart the terminal, and inspect uv tool list.
    qae is not found after pip installationActivate the environment where QAEOps was installed or call its executable directly.
    Unsupported PythonInstall Python 3.12, 3.13, or 3.14 and recreate the environment.
    Workspace missingChange to the intended project and run qae init.
    Invalid configurationBack up the workspace configuration file, correct YAML errors, or intentionally recover with qae init --force.
    Missing workspace directoriesRun qae init again; compatible missing directories are recreated.
    LM Studio unavailableOpen LM Studio, load a model, start the local server, run doctor, then retry models.
    No models listedDownload or load a suitable chat model and restart the local server.
    Request timeoutWait for model loading or increase provider.timeout_seconds.
    Invalid provider JSONUse a model that reliably follows structured JSON. The documented MVP qualification model is qwen/qwen3-4b-2507.
    Editable install dependency errorRun python -m pip install -e ".[dev]" or the documented locked uv sync command.
    Permission failureGrant project read access and write access to the configured reports directory.
    PowerShell blocks activationRun .venv\Scripts\qae.exe directly or use an organization-approved execution policy.
    Docker cannot reach LM StudioUse host.docker.internal and configure a Linux host-gateway when needed.

    Safe failure behavior

    Provider errors use exit code 6 and sanitized remediation. QAEOps does not print tokens, authorization headers, endpoint credentials, raw response bodies, or raw transport exceptions.

    Operational limitations

    • QAEOps 0.1.0 is not published to a public package index.
    • AI-assisted workflows require a running LM Studio server and suitable loaded model.
    • Generated output may be incomplete or incorrect and requires professional review.
    • Hosted CI deliberately does not download models or start LM Studio.
    • Version 0.1 does not support in-place downgrade; test older versions against a copied workspace.
    Local-model release validation is a separate step from hosted CI. Status here describes documented functionality and is not an independent release or security certification.
